## 事件统计：确认问题与新口径

第三方周报称 2026-10-12 至 10-18 塔罗 `tool_start=205`、`tool_success=743`。本轮没有从分析后台独立复核这两个数及其过滤条件，不能据此计算转化率，也不能把差异全部归因于某个源码缺陷。

源码确认如下：

- 塔罗 `tool_success` 的含义一直是当前选牌全部翻开；固定牌阵还要求牌位填满。它不是 AI 解读完成。原 `tool_start` 只在首轮洗牌时触发，之后继续换牌或加牌可再次达到完成条件，却没有对应的新开始；通用 `invalidate()` 又会重置完成标记，导致开始与完成边界不一致。
- `/discover` 的 `BirthdayCardFinder` 在计算成功时发送 `tool_success`，缺少对应的 `tool_start`。
- `/day-pillar` 的计算入口同样没有在提交计算时发送开始事件，反而在“下一步”跳往出生报告的链接上发送 `tool_start(day_pillar)`，把导航混作工具使用。

实现保留既有事件名、工具标识及无个人信息的事件载荷：

- 塔罗以状态跟踪同一轮：首次洗牌开始；同一轮完成前的继续操作不重复开始；满足翻牌条件后只完成一次；完成后实际抽入或替换新牌会开始下一轮；重新开局清空轮次。查看、移动、旋转或反复翻看同一批牌不会重复完成。合法的再次抽牌继续计数，不按访客、日期或牌面去重。未完成便重开可以产生下一次开始，不伪造上一轮完成。
- 两个生日入口在接受一次提交时发送开始，成功或失败后发送对应结果；同步 `inFlight` 标记阻止尚未处理完的重复提交。`/day-pillar` 跳往报告的链接不再冒充开始事件，并补上表单的现有统计标识。
- 统计修复不会把 AI 完成加入 `tool_success`，也不将保存或恢复已有结果当作一次新的计算完成。

涉及 `components/birthday-card-finder.tsx`、`components/day-pillar-experience.tsx`、`components/celestial/tarot-experience.tsx`、`lib/celestial/tarot-analytics.ts` 及相应测试。

## 测试访问识别

提供显式 `?analytics_test=1` 标记，通过当前标签页的 `sessionStorage` 记住测试状态；存储不可用时，仅保留内存状态。标记不包含身份、生日、问题或设备指纹，无需调整安全设置。

标记访问通过 `trackToolEvent`、站内打开事件和分析 URL 的 `beforeSend` 过滤，覆盖当前接入的 Analytics 与 Speed Insights。它用于可控 QA 访问，不是可靠识别所有自动化访问的系统：未加标记的测试、既有历史数据及第三方统计不能据此追溯排除；存储不可用时跨文档导航也不保证保留状态。正式浏览器验证需使用该标记，并记录实际网络或事件证据。

## 文档语言：已处理部分与明确限制

新增根层 `DocumentLanguage` 客户端组件，按受支持的主站路径及 `locale` 同步浏览器 DOM 的 `document.documentElement.lang`，并随客户端导航更新。各已本地化页面原有的服务端 `main[lang]` 保留。

**原始 SSR HTML 的根标签仍固定 `lang="en"`，这一限制尚未解决。** 这次不能宣称“SSR 文档语言已修复”。现有单根 App Router 布局不读取查询参数；在根布局引入 `headers()` 会使其覆盖的全站路由采用动态渲染。为避免这项范围更广的性能变化，本轮没有这样实施，也未迁移整套路由结构。四语言浏览器 DOM 同步已在 320px 实际视口确认；这不改变原始 SSR 根语言限制。
